## 2. Conventions and invariants

- IDs are UUIDs unless labelled provider IDs, SHA-256 digests, or cursors. Client generates UUIDv4 for local transactions and mutations. Money is integer paise. PostgreSQL uses bigint; JSON uses integers constrained to 1–100,000,000,000 paise for a transaction or budget. Reject floats, signs in an amount field, rounding and other currencies. Summaries accumulate in signed 64-bit integers.
- Dates are strict ISO `YYYY-MM-DD`; months `YYYY-MM`; instants UTC RFC 3339. IST determines reporting date if an alert has an exact event time. Store a date-only transaction with a null event instant. For an alert without a reliable transaction date, use received date and set `dateSource=received`. Mark ambiguous date formats for review. Reject future statement dates.
- Text is trimmed, NFC-normalized and stripped of controls. Alias 1–40 chars, household name 1–60, category and merchant labels 1–80, beneficiary label 1–40. Reject account numbers/UPI addresses in labels where recognized and warn that user-entered labels become visible. Render as text. Escape CSV formula prefixes on exported text fields.
- No household or bank data in URLs, log messages, traces, support attachments or analytics. Invite secrets can be displayed once and passed through the OS share sheet as text, not embedded in tracked URLs. Do not send emails automatically in v1.
- One active household per adult, one active registered device per adult, one active owner per household, maximum five adults. A licence attaches to the household and has no expiry after payment, subject to refund and dispute state. Paid ownership and payer visibility are separate.

## 3. PostgreSQL schema

Business data lives in schema `app_private`, outside exposed Data API schemas. Every table enables RLS and defaults to deny for browser/mobile roles. No client grants for business tables. Expose a narrow set of `public` RPC functions to the server role only; revoke default PUBLIC/anon/authenticated execute and qualify all table references. Edge handlers validate user JWTs and pass the verified subject. RPCs recheck membership, device, licence, household and ownership in the same SQL transaction as the operation. Do not trust a caller-supplied actor ID or grant a client privileged credentials. Use checked enum types or CHECK constraints.

Notation: fields are NOT NULL unless marked `?`. All timestamps are timestamptz. All amounts are bigint. Unless stated, deletes are explicit in lifecycle functions. Use compound keys for all cross-entity household references. At minimum index every FK used for joins/cascades plus the indexes below.

Membership creation/acceptance, transfer, household close, shares, refund links and sequence increments lock the same household row first. Operations involving one user in multiple contexts also serialize on an actor lock; canonical order is actor IDs in sorted order, then household IDs in sorted order. Never hold a database lock across Razorpay network calls. Constraint failures map to typed business errors. Set a UTC DB session, cap statement duration, and serialize all data-changing RPC calls on their affected resource rather than trusting UI sequencing.

### Alert pipeline

1. Before access, require a registered device and valid local lease, with a separate capture opt-in. Compatibility probe may request/check permissions, but capture code remains disabled and performs no provider query before activation and consent. Do not request SEND_SMS, contacts, accessibility, or the default SMS role. Notification access is a separate Android system grant.
2. SMS receiver handles incoming broadcasts and assembles multipart messages. Process transient content with a bounded `goAsync` operation and finish promptly. Do not pass raw content to WorkManager input. For recovery, query the inbox with consent and a resumable high-water mark on app open/periodic work; incremental scans require READ_SMS. User-requested initial history reads up to 90 days in pages of 250. Persist a cursor and normalized results only. Notification listener handles posted alerts for the official package allowlist and can restart without duplicating already observed notifications. Missing content, redacted alerts and vendor background restrictions are normal cases.
3. Match sender/package and known template before interpreting. Drop OTPs, promotions, unrelated messages and sensitive-content notifications. Keep parser precedence explicit and version fixtures by institution, instrument, sender, template and direction. Use a pure Kotlin parser returning normalized candidate or typed reason. Parse grouped INR using digit/string operations; ignore balance amounts and identify explicit debit/credit amounts. Do not guess payee or parse unknown templates as high confidence.
4. Generate per-install HMAC fingerprints from stable source identifiers and a normalized alert representation, with a Keystore-protected secret. Store only digests. First deduplicate exact observations. Merge cross-source alerts automatically only when transaction reference digest, direction, amount and instrument are compatible. Without a reliable reference, same amount plus merchant/time is only a suggestion. Repeated payments stay separate unless user confirms. Server deliberately does not infer cross-person duplicates; show similar shared records for review on-device, and ask an author to withdraw their duplicate.
5. Assign high confidence only when the template is known, amount and direction are unambiguous, and date is known or can be marked as received-date. Only high-confidence live expenses matching an approved exact sharing rule may queue an automatic share. Historical and imported records always start private. For refund/reversal, require a confirmed link, validate partial refunds against outstanding amount, and update the original share only with explicit user confirmation.
6. Room transaction atomically updates observation, local record and any outbox item. WorkManager flushes with network constraints and retries. Never persist raw alerts in logs, database, crash reports or transient work files. Opt-in unsupported-format reports let the user preview a redacted sample with placeholders for names, amounts, references and identifiers. Reports are sent only by deliberate user action via their email app.

### Bulk merchant correction

Group by normalized exact merchant key or category. On correction preview, query past records by merchant key and optional account, show the count, let the user select individual matches, and exclude merged or hidden records by default. For past-only changes, update selected records in one Room transaction. For future-only changes, upsert the exact merchant rule. For both, do both in one transaction. When both rule scopes exist, the account-specific match wins; preserve existing manually chosen categories on new duplicate observations. Store undo as version-checked inverse changes for 24 hours. If a record or rule changed since the bulk operation, leave that item alone and report the skipped count. Already-shared records retain their server categories unless the payer separately confirms an update to the shared entry. This flow needs no new cloud endpoint.

### Statement CSV contract

UTF-8 (optional BOM), comma-delimited with RFC 4180 quoting. Header exactly `date,direction,amount_inr,description,reference`. Date ISO, direction `debit|credit`, amount positive decimal with up to two fractional digits and no currency symbol/grouping, description up to 200 chars, reference optional up to 80 chars. User selects the instrument, coverage dates and source file through Android’s document picker. Parse via stream, no persisted file or broad storage permission. Reject invalid headers, malformed quoting, over-limit files, invalid rows and dates outside selected range; show row numbers and reason codes, never partial-commit without a preview. Commit accepted rows only after confirmation. Derive row identity from file hash and row number; on re-exported/overlapping files match exact account+reference+amount+direction first, then show candidates for review. When a statement contradicts an alert, make the alert an excluded/merged observation linked to the statement-backed record and require user review of any existing share. Import is never sent to backend by itself.

## 5. API and authorization contract

**Base URL:** `{SUPABASE_URL}/functions/v1/api/v1`. Public metadata at `GET /release`. Webhook is `POST {SUPABASE_URL}/functions/v1/razorpay-webhook`. Content type `application/json` with 256 KiB request cap, UTF-8. Reject unknown body properties and unsupported fields. Defaults and max limits below. Client uses provider publishable key for gateway access and `Authorization: Bearer <Supabase access token>` for authenticated routes. User claims must be verified, including issuer and expiry. No merchant/payment secrets in web bundle or APK. CORS allows only the configured web origin and necessary headers. Native HTTP does not use browser CORS.

**Device session:** Android generates P-256 key in Keystore, submits SPKI DER base64url and signs the UTF-8 string `FT1:<purpose>:<challengeId>:<installationId>:<nonce>` with ECDSA/SHA-256 (DER signature base64url). Server checks stored nonce hash, key and actor, expiry and one-use status. Registered devices obtain a signed device session bound to actor, device ID and current Supabase JWT session ID. Session valid 15 minutes. Android household APIs require it as `X-Device-Session`; server also verifies active device and active licence on each protected request. Local lease is a separate signed token with `sub,deviceId,householdId,licenceVersion,issuedAt,expiresAt`, maximum 7 days. Verify against an embedded public key; allow current and previous signing key IDs during rotation. Renew after 24 hours when online. After expiry or online denial, stop new capture and hide cached shared data; personal history and export remain behind the local lock. Detect backward clock changes using last accepted server time plus elapsed monotonic time when available; require online renewal when clock state is suspicious. This is a bounded control for the official APK.

**Responses:** success `{"data":...,"requestId":"uuid"}`. Errors `{"error":{"code":"...","message":"...","field":"optional","retryable":false},"requestId":"uuid"}`. HTTP 400 invalid input, 401 expired/invalid auth, 403 insufficient rights or licence, 404 inaccessible/absent resource, 409 conflicts, 410 expired invite or sync cursor, 413 size, 422 semantic validation, 426 obsolete build, 429 throttled with Retry-After, 503 retryable upstream or maintenance. Public download metadata remains available even during maintenance. All mutation routes require UUID `Idempotency-Key` except challenge creation, webhook and sync batches. Same actor/route/key/body replays the prior result or current safe resource state. Different body with same key returns 409. Scope all IDs by actor/household before disclosure.

Use stable error codes `INVALID_INPUT`, `AUTH_REQUIRED`, `REAUTH_REQUIRED`, `DEVICE_REVOKED`, `DEVICE_LIMIT`, `LICENCE_INACTIVE`, `FORBIDDEN`, `NOT_FOUND`, `INVITE_INVALID`, `HOUSEHOLD_FULL`, `ALREADY_MEMBER`, `TRANSFER_REQUIRED`, `VERSION_CONFLICT`, `CURSOR_EXPIRED`, `CURSOR_AHEAD`, `SNAPSHOT_EXPIRED`, `IDEMPOTENCY_CONFLICT`, `SHARE_WITHDRAWN`, `CATEGORY_ARCHIVED`, `INVALID_REFUND_LINK`, `CHECKOUT_CLOSED`, `ORDER_PENDING`, `BUILD_TOO_OLD`, `RATE_LIMITED`, and `TEMPORARILY_UNAVAILABLE`. Machine codes drive app behavior; messages are plain English and never echo raw inputs. Native clients include `X-App-Build` on protected routes and send the version code also when registering/renewing; a 426 blocks further protected calls until update. Browser routes have no APK version requirement.

**Representation shorthand:** `Household={id,name,state,role,licenceState,memberCount}`, `Member={id,alias,role,joinedAt}`, `Category={id,name,seedCode?,archivedAt?,version}`, `Budget={categoryId,month,limitPaise,version}`, `SharedTx={id,payerMemberId,kind,state,amountPaise,reportDate,merchant,categoryId,beneficiaryLabel?,refundOfId?,refundOriginalExpired,version}`. Null means intentionally absent; response omits optional sensitive fields entirely when not applicable. Payer identity comes from membership, never from the request. The first successful authenticated mutation provisions a profile with alias “Member” if needed. The app prompts for a chosen alias before enabling sharing.

| POST `/account/delete` | Auth, fresh Google reauth, `{confirm:true}` | `202 {jobId,state}` via Android or web. Owner must transfer or explicitly close household first when others remain. Allow closure after licence suspension via web support/reauth path. |

For `fresh auth`, verify a new Google ID token on sensitive routes using the configured audience, issuer and subject mapped to the current Supabase user; require Google token `iat` within 10 minutes and one-use server challenge nonce. Do not use the access token’s refresh time as proof of recent user authentication. Sensitive routes consume the nonce only after the request is authenticated. Extend `POST /device/challenges` with purpose `reauth` for both web and Android and an installation ID only for device purposes. Sensitive routes carry `X-Reauth-Challenge` and `X-Reauth-Id-Token`; never log either header. Website deletion/closure uses the same auth, with web actor allowed only for those routes and no shared data returned.

**Mutation shape**

```json
{
  "mutationId": "uuid",
  "entity": "transaction",
  "operation": "upsert",
  "id": "uuid",
  "baseVersion": 0,
  "value": {
    "kind": "expense",
    "state": "included",
    "amountPaise": 85000,
    "reportDate": "2026-11-08",
    "merchant": "Grocer",
    "categoryId": "uuid",
    "beneficiaryLabel": "Household"
  }
}
```

- `entity` is transaction, category or budget. `operation` is upsert or delete. Transaction/category `id` is UUID; budget ID is `<categoryUuid>:<YYYY-MM>`. `baseVersion=0` creates; update/delete requires latest positive version. Values: category `{name,archived}` (seed immutable); budget `{limitPaise}`; transaction as above with optional `refundOfId` required for refund. Delete omits value. Category and budget mutations are owner-only; category “delete” means archive, budget delete removes the budget. Re-sharing a withdrawn payment requires a new shared UUID. For an existing share, amount, kind, report date and refund link are immutable. Reclassifying a purchase updates linked refund categories in the same transaction. Reversing a purchase with counted refunds withdraws those refund entries in the same transaction after explicit user confirmation. Archived categories cannot be assigned to new shares.
- `MutationResult={mutationId,status,version?,code?,serverVersion?}` with status applied/replayed/conflict/rejected. Conflict UI shows fresh server state and allows discarding or explicitly reapplying supported edits. Do not silently overwrite shared records.
- `Change={seq,entity,id,op,value?}` with `entity` household/member/category/budget/transaction; `seq` decimal string; delete omits value. Resolve changed keys to current authorized state, treating absent rows as deletes. Consumer applies rows idempotently. No wallet, bank reference, or private labels are included.

## 6. Sync, accounting, and lifecycle

- All shared mutations allocate change numbers by incrementing the household row inside the write transaction. This prevents a client from skipping late commits. Serialize changes and delete records under that same lock. Bulk member withdrawal emits a member deletion plus tombstones for their records; withdraw linked refunds with their original. Keep payload out of the change log. App-side local create/unshare and local capture are independent from cloud success.
- Incremental sync on foreground (at most once per 60 seconds), explicit refresh, and a network-constrained periodic 30-minute work request. Push locally pending mutations first, then pull. WorkManager may defer background runs. Retry network/503 errors with exponential backoff starting 15 seconds, jitter and 30-minute ceiling. Respect Retry-After. No retry loop on auth, schema, stale version, or lost household. Coalesce unsent edits for the same entity; never change a mutation ID’s contents after first transmission. Apply changes and commit the new cursor in one Room transaction.
- Snapshot recovery: token valid 15 minutes, bound to actor/household/device, records initial committed sequence. Iterate stable `(entity_type,entity_key)` order using the continuation. Stage rows into temporary cache tables while keeping pending local outbox. Current-state pages can include mutations after the watermark, so pull the delta after the watermark until caught up before swapping caches. A row added behind the continuation is recovered by the delta. Abort on expired token, membership loss or watermark older than retained log and restart only after authorization succeeds. No pending item is applied to a different household.
- Keep shared rows for 24 months by IST report month, with a daily bounded prune. Resolve old expense/newer refund dependencies by removing the reference only during retention pruning and preserving the newer refund as an existing counted adjustment with its category; represent it as `refund_of_id=null` plus `refund_original_expired=true` (boolean default false, server-set only). Never admit new unlinked refunds. Deleting a purchase by member action withdraws linked refunds instead. Compact change log and advance `min_cursor` atomically after 30 days. On large removals, stage a visibility tombstone first and prune in chunks without leaking residual records.
- Summaries are deterministic Kotlin reducers over authorized local/shared rows. Use confirmed included expenses and linked/refund-original-expired refunds, with merchant/category updates applied to the source row only when user chooses. A full reversal cancels the original in its original period and contributes no separate expense. Undo reversals through explicit review and conditional updates. Compare each month against its own category limit; calculate progress in integer arithmetic. Do not merge private and shared totals into one figure; a shared expense can also appear in the payer’s personal view without being duplicated within either view.
- Leaving/removal revokes that membership and hides its shares immediately on the server. Removed device caches purge at next check or lease expiry. Owner transfer changes roles, not payment ownership. Owner closure disables all protected operations immediately. Account deletion marks access denied, revokes devices, withdraws shared data, cancels pending invites/transfers and schedules Auth deletion through the admin API; idempotent worker retries if Auth deletion fails. Self-serve request remains usable from web if app is inaccessible. User-facing completion target is 30 days. Unlink billing from deleted profiles. Retain minimized payment records for 180 days as an operational baseline, with documented longer retention only where required for applicable records or active disputes. Backups expire after 14 days; if restored, replay erasures before reopening traffic.

## 7. Razorpay purchase and entitlement

1. Buyer signs in, accepts versioned terms, and calls order creation. In a transaction reserve the local order and receipt, persist the SKU and amount `49900`, and enforce one unresolved order per buyer. Then call `POST /v1/orders` with `{amount:49900,currency:"INR",receipt:<local UUID>,partial_payment:false}`. Never send financial records, bank info, or raw identifiers in notes.
2. Store the provider ID and return checkout fields. For an ambiguous provider timeout, mark `creation_unknown`; never blindly POST a second order. Operator uses the stored receipt in Razorpay Dashboard to recover and bind an exact amount/currency match. Release reservation only after confirming no captured/payment-in-progress order and disabling the old checkout attempt in our app. If no provider result can be established, keep that buyer in pending support rather than risk a duplicate charge.
3. Launch Checkout.js with Razorpay public key ID and provider order ID. Razorpay controls displayed compatible UPI methods. On callback, verify signature against the **stored** order ID and payment ID with API secret. Then fetch provider payment status by ID and compare amount, currency and order. Require captured status, not authorized, before granting access.
4. Webhook signature verification uses HMAC-SHA256 over raw request bytes, a separate webhook secret and constant-time comparison. Require event ID. Parse only after verification. Handle `payment.captured`, `payment.failed`, `refund.processed` and the configured provider dispute events. Deduplicate event IDs and entity IDs. Fetch provider state if an event depends on a missing local payment row. An unprocessable transient returns 503 for provider retry. Valid events are acknowledged only after database application commits or the verified event is safely classified irrelevant. No raw webhook body retained.
5. In one fulfilment transaction lock actor and local order, upsert captured payment, validate no full refund/dispute, attach the paid licence, and create household plus owner/default categories if there is none. Existing owner’s pilot household upgrades in place. If buyer joins another household despite an unresolved checkout or a second charge settles, record payment but do not grant a second licence; flag for operator refund. Captured state cannot regress on a late failed/authorized event.
6. Full processed refund or lost dispute revokes the paid licence. Open dispute suspends; documented win can restore after a provider re-fetch if no processed full refund. Ambiguous dispute resolution stays suspended for operator reconciliation. Refund amount is cumulative across processed provider refunds. A partial refund initiated outside the app does not revoke automatically; flag it for review. Recovery never deletes customer history solely because a payment failed. An owner with a revoked licence can buy again after resolution, reactivating the same open household; a suspended licence blocks repurchase. Refunds and disputes on older orders affect the current licence only if its order ID matches.
7. Enable automatic capture in Razorpay Dashboard. Use owner Dashboard for refunds and provide the customer with the checkout reference and an email support route. Reconcile pending sales and provider settlements daily while checkout is open. Admin scripts require operator credentials, use dry-run by default, and record reason code. No unrestricted admin HTTP endpoints.

**Operational provider fields:** Razorpay webhook supplies `X-Razorpay-Signature` and `x-razorpay-event-id`. Incoming `payment.captured` may arrive before browser confirmation. Verify test/live account identity via separate secrets, project and route. Use key rotation with old webhook secret available during retried events. Store API key ID, API secret, webhook secret and lease signing key only in environment secrets. [Razorpay security checklist](https://razorpay.com/security/checklist/) · [Webhook signatures and retries](https://razorpay.com/blog/payment-gateway-webhooks-india/)

## 8. Security, reliability and release operations

- Validate all business objects again server-side. Authorization checks apply to every read, export snapshot, mutation and lifecycle route. Rate-limit general API to 120 requests/minute per user with route-specific lower limits. All shared state changes use server-issued membership and payer IDs. Test stolen JWT alone, old device key, copied APK, cross-tenant UUIDs, forged webhook, expired invite, household ownership and revoked sessions. Device binding reduces ordinary credential reuse; it does not make local parsing piracy-proof.
- App protects network calls with TLS and disables cleartext traffic. Android build is signed with a dedicated offline-kept production key; R8 enabled for release and mapping stored privately. Secure screen flags cover transaction details and app switcher previews. Use OS-native credential protection. No third-party advertising, behavioral analytics or crash SDK in v1. Log only bounded redacted operational events, parser counters on device, provider identifiers necessary for disputes and request IDs. Website CSP permits Google and Razorpay resources required by Checkout, blocks other third-party scripts and avoids analytics pixels.
- Deploy `pg_cron` SQL housekeeping for local table cleanup, retention and deletion-job staging. An operator command runs external Auth deletions and reconciliation daily; client-visible access is revoked immediately on request. Run daily private encrypted logical DB backups from the operator computer, retain 14 days, and test restore monthly. Store recovery credentials independently, keep an off-device encrypted copy on existing storage, and record when the last backup succeeded. Hold checkout if the last successful backup is older than 48 hours. Target RPO 24 hours and RTO one business day. Local SMS parsing keeps going during permitted offline grace.
- Start on Supabase Free, with 500 MB database, 5 GB uncached egress and 500,000 Edge invocations/month at the published rates. Verify quotas in the project Dashboard and track DB growth, sync frequency, failed webhook count, p95 duration, outstanding deletion jobs and oldest unresolved order. At 70% take action; at 85% pause sales if runway is under seven days. Probe public health without reading customer data. Free hosting and retention are a launch budget assumption. [Supabase pricing](https://supabase.com/pricing) · [Edge Functions pricing](https://supabase.com/docs/guides/functions/pricing)
- Use explicit `checkoutMode` and a release-wide notification parsing kill switch. Emergency response order: stop checkout, disable affected capture/template or sharing path, preserve redacted evidence, fix and ship signed upgrade, verify in staging, notify affected customers where required. Prefer additive migrations and forward fixes. Keep previous APK and source tag for diagnosis; Android downgrade is not the customer rollback plan. If old client is incompatible, minimum version is enforced online and download instructions remain accessible.
- Accessibility: Compose semantics for amount and category, text at 200% scale, screen-reader order, visible focus, contrast, meaningful statuses beyond color and 48 dp minimum touch targets. Test screen-reader payment recovery and consent flow. Performance goals: cold home under 2.5 seconds on a representative midrange phone with 10,000 local records, capture processing under 500 ms typical after alert delivery, and p95 sync pull under two seconds under pilot load. Measure and record device/network profile.
